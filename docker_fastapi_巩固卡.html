② 今晚读 · FastAPI 最小骨架 理解+会改

from fastapi import FastAPI

app = FastAPI()                 # 开店（应用实例）。抄模板，闭眼会敲即可

@app.post("/login")             # 门牌：POST + 路径/login。路径你要会改
def login():
    return {"msg": "登录成功"}  # ← 这里面的逻辑才是你的活儿，要会自己写
app=FastAPI() 理解+会改 @装饰器挂路由 理解+会改 函数里return的逻辑 必须自己写

读的时候只问自己一句："哪行是脚手架、哪行是我的业务逻辑？" 分清楚就达标。

⚠️ 为什么这里没配 BaseModel？这段是"最小骨架"，只演示开店+挂路由+返回固定话，不接收客户端任何数据，用不着"收数据的碗"。BaseModel 是给进来的请求定格式的（碗），只有要收客户端传来的东西才配——见 ⑧-1 的 /chat 才出现。所以"POST 常配 BaseModel"指的是真正要收数据的 POST，本段是教学最简版、还没走到那步。

🔑 def login() 只是"定义一个函数"，它自己不知道挂哪个路径——路径由上面那行 @app.post("/login") 决定。"如果是 /login 就交给 login 处理"是装饰器的分派工作；函数体里的 return 才是"进门后回啥"。函数名 login 可随便改（如 def handle():），URL 仍是 /login，名字只给人看、不影响路由。

🗂️ @app.post("/login") 是往路由表"登记/挂牌"（启动程序时把规则存进 app）；真正"查路由表"是每次请求进来时 FastAPI 自动做的，你代码里看不到查的那行。即：app.post = 填表/挂门牌（登记）；查表 = 客人来了服务员对菜单（框架隐式行为）。

📌 对照：把上面换成 @app.get("/") 长这样（浏览器地址栏直接敲 localhost:8000/ 就能看到返回，因为浏览器默认发 GET 请求）：

from fastapi import FastAPI

app = FastAPI()                 # 开店（应用实例）。【理解+会改】

@app.get("/")                   # 门牌：GET + 根路径/。浏览器直接敲就能进【理解+会改】
def home():
    return {"msg": "欢迎光临"}  # ← 这里面的逻辑才是你的活儿，要会自己写【必须自己写】

🔗 觉得 @app.get("/") 和 def home(): 没关联？其实强关联：@ 装饰器必须紧贴在它要修饰的函数正上方，Python 会把下面那个函数当参数传进去登记。等价写法（不用 @ 语法）一看就懂：先 def home():... 再写 app.get("/")(home)。即 @app.get("/") 就是 app.get("/")(home) 的简写——"把 home 这个柜台，挂到 / 这个门牌"。两行不是各管各的，是挂牌动作指向这个函数。

②-b 今晚读 · uvicorn 是什么（开门的服务员） 理解为主

uvicorn main:app --reload --host 0.0.0.0 --port 8000

你的 main.py 只"定义"了 app（菜单+厨房），自己不会开门接客。uvicorn 是独立的服务器程序（ASGI 服务器），负责监听端口、等 HTTP 请求、把请求递给 app、把 app 的 return 转成响应送回去——就是"服务员+大门"。没它，python main.py 啥也不会发生（没人告诉 Python 去监听端口）。

逐段拆：main=文件 main.py（去后缀）；app=文件里的变量 app（FastAPI 实例），uvicorn 去把它找出来；main:app 的冒号="文件:变量"。--reload=改代码自动重启（开发用，生产别加）；--host 0.0.0.0=监听所有网卡（容器/服务器让外部能访问；本机用 127.0.0.1 也行但 0.0.0.0 通用）；--port 8000=监听 8000 门牌。

接客流程：启动后 uvicorn 在 8000 蹲着 → 请求到 → 解析方法+路径交给路由表匹配 → 执行对应函数拿 return → 转成 JSON 响应送回。容器里也靠它：Dockerfile 的 CMD 就是自动跑这条命令，里面监听的 8000 正是 -p 8000:8000 接的那扇门（--host 0.0.0.0 才能让外部进）。

🔍 --host 0.0.0.0 和 --port 8000 不是"双向"，是监听地址的两个坐标：host=在哪些网卡/IP上听（0.0.0.0=这台机器所有网卡的入口都听），port=听哪个门牌（8000）。两者合起来="在机器所有入口的 8000 门牌上蹲着等请求"。uvicorn 是被动服务器，只"等请求来→处理→回应"，不是主动双向通信；接收请求和返回响应是同一次连接的两个方向，不是"双向监听"。

🏠 纠正：8000 不是"本机"，它是端口（门牌号）。本机是 IP/楼（如 127.0.0.1），一台机器上可有成千上万个端口（80、443、8000…）。正确说法：uvicorn 在"本机的 8000 门牌"上蹲着听。组合"本机IP:8000"才是完整接入点——楼（IP）+ 房间号（8000）。前面"-p 前面本机"那个"本机"指 IP/楼，8000 是房间号，两码事。

main:app = 文件:变量 理解 --reload/--host/--port 会改 "uvicorn 是开门服务员"要理解透

③ 今晚读 · Dockerfile 说明书 理解为主·会改端口/依赖

FROM python:3.11                       # 基础系统：拿现成的 Python 环境

关键记忆：uvicorn 不在你的 .py 里，而是在说明书最后一行 CMD 启动。这就是"服务员开门"写在哪。

④ 今晚记 · 跑容器的命令 记死口诀

docker build -t myshop .        # 封箱成镜像，起名 myshop
docker run -p 8000:8000 myshop  # 开门：本机8000 接 容器8000

口诀："-p 前面本机、后面容器"。忘了写 -p 店照跑但外面进不来。push 上货架不需要 -p，两件事平行无关。

🔗 "容器 8000"= 容器里那间店（uvicorn）监听的端口（房间号），由 Dockerfile 的 CMD --port 8000 决定。-p 本机:容器 的第二个数必须 = 容器里 uvicorn 蹲的这个数。改了 uvicorn 监听 9000，就得写 -p 8000:9000（本机8000 接 容器9000）。

⚠️ 术语分清楚："打包的产品"是镜像 image（死的模板），容器 container 是镜像跑起来后的活实例——别把俩词混成一个。端口号写死在镜像的 Dockerfile 里（--port 8000），容器从镜像跑起来后 uvicorn 就听那个 8000，所以 -p 第二个数必须跟它一致，管子才接得进。

🌐 本机 run -p 的访问范围：你自己（localhost:8000，自测）✅ + 同 WiFi 的人（你笔记本局域网IP:8000）✅；但公网陌生人 ❌进不去（路由器 NAT 挡着）。所以笔记本跑主要是自测 + 局域网给别人试。要全网能进，得把容器 run 在云服务器（有公网 IP）上。

⑧-2 真实 LLM Agent 结构（今晚只读，理解整体流程）

from fastapi import FastAPI
from pydantic import BaseModel
from openai import OpenAI

app = FastAPI()
client = OpenAI()    # 需要 API key（放 .env，第4章讲，别写死在代码里）

class Req(BaseModel):
    user_msg: str

@app.post("/agent")
def agent(req: Req):
    sys_prompt = "你是一个简洁的查资料助手。"   # ← 人设/规矩，必须自己写
    resp = client.chat.completions.create(       # 调 LLM（脚手架：理解这步在干嘛）
        model="gpt-4o-mini",
        messages=[{"role":"system","content":sys_prompt},
                  {"role":"user","content":req.user_msg}]
    )
    return {"reply": resp.choices[0].message.content}
端点结构 / BaseModel / 怎么传消息 理解+会改 sys_prompt 人设 / 选模型 / 要不要用工具 必须自己写

整条流水线一句话：写 .py(店) → 写 Dockerfile(说明书) → build(封箱) → run -p(开门) → 别人 POST 你的 /chat 或 /agent → 你的 Agent 干活返回。
你"写不出"的永远是 sys_prompt 和 reply 逻辑 这两类——它们才是 Agent 的核心，其余都是脚手架。今晚只把 ⑧-1 读熟、把"脚手架 vs 业务逻辑"的分界记牢，明天从空白写 ⑧-1 就够。

⑨ 长版 w3_agent_full.py 详细版（Agent 大脑）+ 整合闭环 关键

这就是"你写的 Agent 连接大模型的模板"——Agent 的大脑。它自己是个终端脚本（python w3_agent_full.py 跑），不能联网给别人调。要"接给别人用 + 自测"，得给它套上 ⑧-2 的 FastAPI 外壳。两者拼起来 = 真毕业版，见本卡末尾"整合闭环"。

import os
import json
from openai import OpenAI

# ===== 1. 连接大模型 =====
client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],   # 从环境变量取密钥【理解+会改：换家/换key改这】
    base_url="https://api.deepseek.com",      # 用哪家大模型的服务地址【理解+会改】
)

# ===== 2. 真实函数：模型调工具时真正干活的（你的业务逻辑）=====
def 加法(num1, num2):                          # 【必须自己写】工具背后的真本事
    return f"{num1} + {num2} = {num1 + num2}"

# ===== 3. 工具说明书：告诉模型"你有个 add 工具可用"（name/参数必须英文）=====
工具清单 = [                                    # 【必须自己写】agent 会用啥工具就列在这
    {
        "type": "function",
        "function": {
            "name": "add",
            "description": "计算两个数字相加的和，当用户问加法、求和、几加几时用",
            "parameters": {
                "type": "object",
                "properties": {
                    "num1": {"type": "number", "description": "第一个加数"},
                    "num2": {"type": "number", "description": "第二个加数"}
                },
                "required": ["num1", "num2"]
            }
        }
    }
]

历史 = []   # ← 整个对话历史，跨所有问题保留（记忆来源）【理解：这就是"记忆"】

# ===== 4. 问题列表：第1个多步推理，第2个考跨轮记忆 =====
问题列表 = [                                    # 【理解+会改：换成你自己的问题】
    "帮我算一下，先算 3 加 5，再用这个结果加 10，最后是多少",
    "我刚才让你算的第一个算式是什么？最后结果是多少？",
]

# ===== 外层 for：一个问题一个问题地聊（多轮）=====
for 问题 in 问题列表:
    历史.append({"role": "user", "content": 问题})
    print(f"\n你：{问题}")

    轮次 = 0
    最大轮次 = 10            # 每个问题最多推理 10 步【理解：防死循环护栏】

    # ===== 内层 while：多步推理，直到模型给最终答案（Agent 大脑核心）=====
    while 轮次 < 最大轮次:
        轮次 += 1
        print(f"--- 第 {轮次} 轮 ---")

        resp = client.chat.completions.create(
            model="deepseek-chat",             # 【理解+会改：换模型名】
            messages=历史,                     # 把记忆一起发给模型
            tools=工具清单,                    # 把工具清单交给模型
            tool_choice="auto",
        )
        回复 = resp.choices[0].message

        if 回复.tool_calls:
            # 模型要调工具 → 执行 → 结果喂回历史 → 继续循环（不退出）
            历史.append(回复)
            for 调用 in 回复.tool_calls:
                函数名 = 调用.function.name
                参数 = json.loads(调用.function.arguments)
                if 函数名 == "add":
                    结果 = 加法(参数["num1"], 参数["num2"])   # 【必须自己写】真正执行
                    print(f"  [执行工具] add({参数['num1']}, {参数['num2']}) -> {结果}")
                历史.append({"role": "tool", "tool_call_id": 调用.id, "content": str(结果)})
            continue
        else:
            # 模型给了最终文字 → 任务完成 → 跳出内层循环，进下一个问题
            print("模型：" + 回复.content)
            break

    if 轮次 >= 最大轮次:
        print("⚠️ 达到最大轮次，强制结束（防止死循环）")

print("\n=== 全部问题处理完毕 ===")
client 连接 理解+会改 真实函数/工具清单 必须自己写 历史=记忆 理解 while+tool_calls 大脑核心 必须懂

🔑 四块分工：①连接大模型（client，理解+会改 key/模型/base_url）；②真实函数（加法，必须自己写——agent 的真本事）；③工具清单（告诉模型能用 add，必须自己写）；④历史（跨轮记忆，理解）；⑤while 循环+tool_calls（大脑核心：模型可多次调工具直到给最终答案，必须理解透）。while + tool_calls + 历史 三件套就是 Agent 跟"普通一次聊天"的本质区别。

🔀 关于"模型不选择用工具"：外层 if 回复.tool_calls: 的 else 分支就是干这个的——模型没调工具、直接给最终文字时，打印并 break 跳出循环。你担心的"不调工具"情况没少写。真正没 else 的是内层 if 函数名 == "add":：那是"模型调了工具但名字不是 add"的情况；本脚本只注册了 add 一个工具不会触发，所以安全。要更稳可补 else: print("未知工具") 兜底。

🔀 分支分工再点清：if 回复.tool_calls:（模型决定调工具）→ 执行工具 + continue 继续循环，绝不在此出口；else:（模型决定不调工具）→ 打印最终答案 + break 退出。最终答案永远从 else 出来，但它是"模型调完工具后、这轮决定不再调了"才到达的——不是"调用工具得出了答案=走 else"。tool_choice="auto" 就是让模型每轮自己选走 if 还是 else。关键点：if/else 是每一轮都重新判断的，不是"先调后不调"才合法。"模型从最开始（第 1 轮）就不调工具、直接回答"走的也是同一个 else → 打印 → break，while 只跑 1 次就收工，和"调了 3 轮后第 4 轮才不调"用的是同一个 else，区别只是循环跑了几次。所以"首轮直接答"不是 bug、是正确设计——不需要工具时硬调才错。

🔍 内层 for 循环逐行复盘：回复.tool_calls 是模型这轮写下的"点单小票"列表（可能含多个工具调用，也可能为空→走 else）。for 调用 in 回复.tool_calls: = 一张张取出小票逐个处理（模型调了几个工具就循环几次）。调用.function.name = 这道"菜"的名字（字符串，如 "add"）→ 存入 函数名。调用.function.arguments = 这道菜的参数，但模型只能发文字，所以它是 JSON 格式的一段字符串（如 '{"num1":3,"num2":5}'），不能直接用 参数["num1"] 取。json.loads(...) = "把 JSON 文字还原成真正的 Python 字典"（loads 的 s = string），转完才能 参数["num1"] 取值。两行"取名字/取参数" = 【理解+会改】脚手架（OpenAI 系工具调用的固定拆法）；if 函数名 == "add": 结果 = 加法(...) = 【必须自己写】你的业务逻辑（决定调哪个函数、怎么执行）。

🌐 整合闭环（今晚所有东西合起来）：你写的这个 Agent 大脑（⑨） + ⑧-2 的 FastAPI 外壳（把 /agent 函数包成网页能调的接口） + ③ Dockerfile 把整间店装进集装箱 + ④ run -p 8000:8000 开门。

⑨-b 毕业版：给大脑套上 FastAPI 外壳（= ⑧-2 外壳 + ⑨ 大脑合体）

把上面 w3_agent_full.py 的 while 大脑塞进一个 run_agent() 函数，外面套 FastAPI 的 /agent 接口。① client / ② 加法 / ③ 工具清单 三个直接复用上面，不重复写。注意：API 版每请求新建 历史（无状态，演示用）；真实多轮对话要按用户 session 保留——这点先记着，明天不要求写。

from fastapi import FastAPI, BaseModel

app = FastAPI()                    # 开店（应用实例）【理解+会改】

class AgentReq(BaseModel):         # 收客户端发来的消息（有外部输入→用 BaseModel）【理解+会改】
    消息: str

# 把 w3_agent_full.py 的 while 大脑，封装成一个函数（复用上面 ①client ②加法 ③工具清单）
def run_agent(用户消息: str) -> str:
    历史 = [{"role": "user", "content": 用户消息}]   # 每请求新建历史（演示；真实多轮用 session）
    轮次 = 0
    最大轮次 = 10
    while 轮次 < 最大轮次:
        轮次 += 1
        resp = client.chat.completions.create(
            model="deepseek-chat",
            messages=历史,
            tools=工具清单,
            tool_choice="auto",
        )
        回复 = resp.choices[0].message
        if 回复.tool_calls:
            历史.append(回复)
            for 调用 in 回复.tool_calls:
                函数名 = 调用.function.name
                参数 = json.loads(调用.function.arguments)
                if 函数名 == "add":
                    结果 = 加法(参数["num1"], 参数["num2"])   # 【必须自己写】真执行
                历史.append({"role": "tool", "tool_call_id": 调用.id, "content": str(结果)})
            continue
        else:
            return 回复.content     # 最终答案（从 else 出，前面讲过）
    return "⚠️ 超过最大轮次"

@app.post("/agent")                # 门牌：POST + /agent【理解+会改】
def agent(req: AgentReq):          # BaseModel 接住客户端消息【理解】
    return {"reply": run_agent(req.消息)}   # 【必须自己写】调大脑、回结果
