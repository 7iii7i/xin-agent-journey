RAG 总览卡

电商客服 v2 · Agent 进阶 = 检索增强生成过关

RAG = 检索增强生成：回答前先去你的知识库检索相关资料，塞进 prompt 再让 LLM 答
解决「模型不懂你的私有数据 / 会瞎编」。你 v2 的「商品库搜索」本质就是最朴素的 RAG，真 RAG 只是把「精确查」升级成「意思相近查」。

一、朴素 RAG vs 真 RAG（对照）

朴素 RAG（你项目早期）
用户问 → 工具去 shop.db
→ 关键词 / SQL LIKE 查
→ 结果塞 prompt → 答
靠「字面相等」匹配。用户换个说法（"东西寄回去行不行"）就查不到 / 查错段。
真 RAG（v2 加的 kb_search）
文档切片→向量化→存库
提问→向量化→比相似
→ 捞最像的原文 → 答
靠「意思相近」匹配。问法千变万化也能命中正确资料。
懂框架 面试一句话：早期用 SQL 关键词查（朴素 RAG），后来升级成向量检索处理口语化提问。两者都是 RAG，只是检索方式不同。

二、rag.py 三个方法（你只需懂干嘛）

  • 构建()：文档切片 → embedding 变向量 → 存盘（只跑一次，构建知识库.py 触发）
  • 加载()：服务启动时把磁盘上的向量文件读回内存变量（之后检索全在内存算，快）
  • 检索()：问题变向量 → 和库里比余弦相似度 → 取 top-k 最像的原文当资料返回
懂框架 两个内存变量分工：向量矩阵负责「找」（比相似）、片段列表(原文)负责「给」（捞真句喂 LLM）。向量是原文经 embedding 单向提炼出的「语义指纹」，变不回原文，所以两者必须都存。

三、它怎么挂进你项目（死记这一行）

注册表.注册(
  {... "name": "kb_search" ...},
  知识库实例.检索接口)
死记 这一行和之前 search_product / get_price / get_stock 那三行一模一样——就是往工具注册表多挂一个工具。Agent 层一行没动，模型看 SYSTEM 提示自动决定用 kb_search。

四、rerank 重排（两阶段检索）

粗排 bi-encoder 双塔
问题 / 文档 各自独立
编码成向量
向量预存·查得快·但粗
你项目 kb_vecs.npz 就是预存的文档向量。从 1000 段快速捞回 top-20。
精排 cross-encoder 交叉
问题 + 文档 拼一起
同时看·现算分数
准但慢
只对粗排捞回的 20 段逐段打分重排，取最准的 top-3。
懂框架 为什么分两步：cross-encoder 更准但不能预存（要和问题拼一起现算），全量 1000 段实时跑太慢。所以先用 bi-encoder 预存向量快捞候选，再用 cross-encoder 只对候选精排——速度和精度权衡。你项目目前只有粗排那一步。

五、进阶三块（面试聊取舍）

  • 切片 chunking + 重叠：长文档切段再向量化；重叠防答案被切断丢失（大了精度粗、小了易切散）。
  • rerank 重排：见上——粗排捞全、精排排准。
  • 评估指标：用评估集（问题+标准答案）跑 召回率 Recall（该找的段找没找到）/ 命中率 Hit Rate（前几条有没有对的）/ 忠实度 Faithfulness（答的能不能在资料里找到依据）。让每次优化有数据对比。
懂框架 三块全部「懂框架」即可，不用能手写 rerank 模型或评估脚本。

六、学到什么程度

死记 以下要能认得出、讲得清：

  • 注册表多一行：kb_search 挂在工具注册表里，和另三个工具同套路
  • 三方法名：构建 / 加载 / 检索（干嘛即可，不用背代码）
  • rerank 两阶段：粗排 bi-encoder 预存向量捞 top-k → 精排 cross-encoder 现算取 top-n

懂框架 以下能讲清即可，不用背：

  • 朴素 RAG（关键词）vs 真 RAG（语义向量）的区别与取舍
  • 向量 vs 原文：向量负责找、原文负责给，向量不可逆回原文
  • embedding = 把文字变成「语义坐标」的一串数字（DeepSeek 无此接口，故用本地 bge 中文模型）
  • 加载() = 启动把磁盘向量读回内存，之后检索快
  • 切片重叠 / 评估三指标的含义
