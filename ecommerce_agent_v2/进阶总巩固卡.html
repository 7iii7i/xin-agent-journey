A. Tier 2 · 异步全链路 [代码]

死记核心 Agent 三件套逻辑一字没变，只是整体 async，且最终轮改成流式打字机。

async def 跑_agent(历史: list):
    消息 = [{"role": m["role"], "content": m["content"]} for m in 历史]
    消息.insert(0, {"role": "system", "content": SYSTEM})
    轮次 = 0
    while 轮次 < 10:                       # 最多 10 轮防死循环
        resp = await client.chat.completions.create(
            model=配置.MODEL, messages=消息,
            tools=注册表.清单(), tool_choice="auto")
        回复 = resp.choices[0].message
        if 回复.tool_calls:                  # ① 工具轮：非流式，干净拿工具+参数
            for 调用 in 回复.tool_calls:
                结果 = await 注册表.调用(调用.function.name, json.loads(调用.function.arguments))
                消息.append({"role": "tool", "tool_call_id": 调用.id, "content": str(结果)})
            continue
        stream = await client.chat.completions.create(
            model=配置.MODEL, messages=消息, stream=True)
        async for chunk in stream:           # ② 最终轮：流式逐 token
            d = chunk.choices[0].delta
            if d.content:
                yield d.content              # 吐给前端（打字机）

懂框架 异步传染：一个函数 async 了，调用它的整条链都得 async（db 改成 aiosqlite → 注册表.调用 加 await → 跑_agent 加 await）。工具轮非流式、最终轮流式的设计：工具轮要拼 tool_calls 碎片，非流式一次拿全最省心；最终轮要打字机，才开 stream。

A2. SSE 流式推送 [代码·死记两行]

# main.py 55 行：SSE 格式，每行 "data: 内容\n\n"
yield f"data: {json.dumps(token, ensure_ascii=False)}\n\n"

# main.py 64 行：用 StreamingResponse 把事件流包成 SSE 接口
return StreamingResponse(事件流(), media_type="text/event-stream")

死记 这两行就是"一截一截推给前端"的关键。55 行把每个 token 包成 SSE 格式（json.dumps 防特殊字符炸）；64 行声明这是 text/event-stream 流。前端用 fetch + getReader 按 \n\n 切流读取。

A3. aiosqlite 异步数据库 [代码]

# db.py：sqlite3 → aiosqlite，每行前面加 await
async def 初始化(self):
    async with aiosqlite.connect(self.库名) as db:
        await db.execute("CREATE TABLE IF NOT EXISTS products (...)")
        await db.commit()                    # 四步套路：connect→execute→commit/fetchall→close

死记 异步四步套路和同步版一模一样，只多 await + 用 aiosqlite.connect。懂框架 异步后"查库等待"期间事件循环能去服务别的请求，并发量才上得来。注意：__init__ 里不能 await，所以建表挪到 main.py 的 lifespan 里启动再 await 初始化()。

B. Tier 3 · Docker + 测试 + README [白话]

B1. Docker 容器化 懂框架

  • Dockerfile：镜像配方，怎么把项目装进容器（FROM / COPY / RUN / CMD）。分层缓存：先装依赖再复制源码，改代码不重装包。

双身份：①检验——能 build 跑起来 = 环境可复现（依赖齐、换机器能跑）；②交付——工业级标准打包，面试官看得到。中文编码兜底、端口映射、volume 持久化都是生产约定。

B3. README 懂框架

C1. 朴素 RAG vs 真 RAG [白话·懂框架]

朴素 RAG（项目早期 search_product）

用户问 → 工具去 shop.db → 关键词 / SQL LIKE 查 → 答。靠"字面相等"匹配，换个说法就查不到。

真 RAG（v2 的 kb_search）

文档切片→向量化→存库；提问→向量化→比相似→捞最像原文→答。靠"意思相近"匹配，问法千变万化也命中。

懂框架 两者都是 RAG，只是检索方式不同。口语化提问（"东西寄回去行不行"）绕开字面关键词，只有语义检索兜得住。

C2. embedding 向量化 [白话·懂框架]

把一段文字变成"一串数字"（向量）。意思相近的文字，这串数字也相近——像给句子发"语义坐标"。它是单向提炼：向量变不回原句（指纹≠照片）。本项目用本地中文模型 BAAI/bge-small-zh-v1.5（DeepSeek 只有对话接口、无 embedding 接口）。

懂框架 只懂"embedding = 把人话翻成可比距离的语义坐标"即可，不用能手写模型。

C3. rag.py 三个方法 [代码]

死记三方法 就这三个：构建 / 加载 / 检索。

def 构建(self):                              # ① 切片→变向量→存盘（跑一次）
    self.片段列表 = 片段
    vecs = 模型.encode(self.片段列表, normalize_embeddings=True)
    self.向量矩阵 = np.asarray(vecs, dtype="float32")
    np.savez(_向量文件, 向量=self.向量矩阵)   # 存向量
    json.dump(self.片段列表, ...)             # 存原文

def 加载(self):                              # ② 启动读回内存
    d = np.load(_向量文件)
    self.向量矩阵 = d["向量"].astype("float32")
    self.片段列表 = json.load(...)

def 检索(self, 问题, top_k=3):               # ③ 比相似取 top-k

    idx = np.argsort(-sims)[:k]              # 从大到小取前 k

C5–C8. RAG 进阶四块 [白话·懂框架]

C5. 向量矩阵 vs 片段列表：向量负责"找"（比相似度），原文负责"给"（捞真句喂 LLM）。向量不可逆回原文，所以两个都存。

C6. rerank 两阶段：粗排 bi-encoder（文档向量预存、查得快、但粗）先捞 top-20 → 精排 cross-encoder（问题+文档拼一起现算、准但慢）只对候选重排取 top-3。分两步是速度与精度权衡（cross-encoder 不能预存，全量现算太慢）。

C7. 切片重叠 + 评估：长文档切段再向量化，留重叠防答案被切断；评估用 recall（该找的段找没找到）/ 命中率（前几条有没有对的）/ 忠实度（答的能否在资料找到依据），让每次优化有数据对比。

C8. RAG 不替代 SQLite：SQLite 管精确数字（价格/库存），RAG 管语义文本（政策）。两者并存、模型按"问题要什么数据 + 工具描述"自己选——判据是数据类型，不是口语化程度。

懂框架 这四块全部"懂框架"即可，面试能聊清取舍，不用能手写。
